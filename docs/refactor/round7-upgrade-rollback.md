# 第七轮：工程验证版升级、成套恢复和回滚

仅适用于离线包约定的单机容器化 Linux/arm64 环境与合成任务。原应用默认入口保持原样。本文件不授权生产数据库变更。

## 约定版本与数据边界

旧版本为 `1386a4f68afbe00d83bb355632e9ff7637a227c2` 的核心、API、Worker 和数据库迁移。离线包为它提供与候选版相同的运维封装，镜像分别为 `cpag-engineering:baseline-1386a4f` 和 `cpag-isolated:baseline-1386a4f`；封装不是旧提交原有功能。新版本标识和镜像内容哈希以包内 `release.json` 为准。

本轮不新增破坏性数据库迁移。应用迁移由数据库内名称与 SHA256 登记，并与实际迁移同事务提交。运行实例应独占指定数据根、项目名称和端口。

回滚恢复**旧检查点及旧程序**，不将升级后新增任务强行并入旧数据库。新增任务、产物与控制记录必须先保存到候选版成套快照及保留目录，可在候选版独立环境重新恢复查询。此范围不承诺任意历史版本兼容，也不承诺多主机执行恢复。

## 检查点工具

`scripts/backup/engineering.py` 在已验收的 `bundle.py` 基础上，增加整个数据根（输入、产物、控制回执、配置和容量账本）清单。快照含身份凭据，目录权限须保持私有，不进入 Git 或公开验收附件。

1. 停止提交，等待所有任务进入终态。无退出证明的任务不能强制转终态，应按运维手册核查，检查点暂不通过。
2. `cpag.sh maintenance` 停止 API、控制器、恢复器及证据服务，保留数据库。
3. 工具检查该项目无运行服务、当前根范围内无剩余计算容器；数据库快照检查终态及 attempt 退出证据。使用数据库 SHARE 锁和导出快照复制数据，再核验全文件清单及数据库前后状态。
4. 账本必须属于当前共享根，预留总量不得低于已存储 attempt 文件。工具不会清零或代替容量重建。
5. 运行 `backup --project PROJECT --root ROOT --bundle NEW_PATH --version SOURCE_VERSION`。只有最终 `snapshot.json` 存在且 `verify` 通过，才是有效快照；中途失败目录保留检查。

上述命令通过离线包的可信操作镜像运行，挂载数据根的父目录、快照目录和 Docker socket。计算容器不获得这些权限。

## 独立恢复与回滚步骤

1. 保留源快照，先执行 `verify --bundle PATH`。完整清单包括控制证据、容量账本、原始输入、数据库转储和产物；缺失或篡改必须失败。
2. 使用全新数据库卷，创建空的 `m4_validation` 数据库。配置中数据库密码应与快照一致，不把密码写入操作日志。
3. 恢复目标使用与源相同的绝对数据根，但位于隔离实例；源服务必须停止。目标目录必须不存在，数据库 public schema 必须为空。已有目标、已有恢复报告和非空数据库均拒绝覆盖。
4. 运行 `restore --project TARGET_PROJECT --root ORIGINAL_ABSOLUTE_ROOT --bundle PATH --confirm SNAPSHOT_JSON_SHA256`。确认值来自实际核验的 `snapshot.json`。
5. 成功报告须同时确认数据库行、attempt 历史、文件清单、原始证据引用和容量账本。历史 Docker daemon 标识原样保留为历史证据，不将它改写为新 daemon 的退出证明。
6. 启动所选版本，实际查询恢复任务、证据和下载结果。回滚必须启动基线镜像并完成新合成任务，不能只停止候选服务。
7. 任一步失败都保留部分目标和失败报告，不启动应用；重新使用新的独立目标排查重试，不在旧数据上反复覆盖。

## 可重复演练

`scripts/release/validate-upgrade-rollback.sh` 只能在显式声明的、已断公网的临时 Docker host 内运行。固定使用新的 `/round7-drill`，已有目录则拒绝运行。顺序为：

旧核心实际执行两类合成任务 → 基线检查点 → 候选版升级并查询旧证据 → 新任务 → 候选检查点 → 新项目和新数据库卷恢复 → 旧检查点恢复到第三个项目 → 基线核心查询旧结果并实际执行新任务。

每一代原文件保留为 `preserved-*`，数据库卷独立保留；脚本不删除已有检查点或数据库。正式验收结果及实际镜像标识补记在本轮总报告和 `validation-round7`，未运行前不视为通过。
