# 第十六轮补验收：历史预检与运行门禁

基线 b208bc9，原16项CI通过不覆盖本轮发现的顺序缺陷。第十五轮保留通过；第十六轮重新打开，不进入第十七轮。独立材料已阅读，原样脚本在基线上实际复现，结果见 `validation-round16-supplement/before.json`；可移植保留夹具 `scripts/validation/round16_review_reproduce.py` 只调整仓库/输出位置，不改场景。

## 有限变更

1. 每条预检保存不可变快照：当时文件身份/路径/哈希/长度/角色，来源/批次/授权，配置ID/版本/原件哈希/指纹，以及实际传给核心的 manifest；精确JSON文本及SHA256一起保存。备份按该快照校验、重算报告，不以当前全部文件重解释历史。
2. 运行必须携带 `preflight_id`。服务端核验预检、当前原件/目录和明确双源配置，将预检引用和既有 m4 job/run binding 同事务发布。缺材料、冲突、无映射/时间依据、检查后改变均拒绝且审计，无任务或绑定。UI/CLI不另建规则。
3. 对旧无快照记录提供停写后的显式重建工具；只能在历史时点的文件集合和原配置严格重算一致时标为 reconstructed，不能冒称原始记录已有门禁。不能重建的原报告保留并明确阻断可信备份，不删除或跳过。
4. 统一非法 source_kind 为预登记的400；OpenAPI、前端和CLI/直接API错误语义一致。真实声明继续只接收未核验，不通过synthetic绕过接收条件。

## 预先退出条件

| 顺序场景 | 必须结果 |
|---|---|
| PCAP上传→单源预检→完整备份→补CSV→双源预检→终态完整备份/空库新目录恢复 | 两份报告及各自快照均可API核对；首次一文件、第二次两文件，不丢旧报告 |
| 再追加原件/配置版本 | 历史报告、已完成运行及其证据不变；旧预检不得用于改变后的新运行 |
| 篡改原件或历史快照 | 预检/运行/可信备份明确拒绝；校验恢复后正常，不能跳过历史 |
| 缺来源/批次/授权、批次冲突、无映射/时间依据、预检后变更 | UI普通点击、CLI、直接API给出一致代码/原因；job/binding数量不增，审计存在 |
| 材料齐全合成正例 | 正式Go→真PG→既有隔离Worker→结果/四原始证据；恢复后同样可查询 |
| 历史升级 | 原预检/运行不删除；成功重建明确标注，不能重建明确保留原因；错误不被伪装为通过 |
| 回归与交付 | 受影响Go、数据库、服务、备份、浏览器回归通过；最终提交完整CI全部成功后方可关闭补验收 |

本轮不改关联算法、协议范围、冻结RC1或默认入口，不将这些软件缺陷转列真实材料阻塞。原R16“全部门槛通过”由本补验收记录修正，已有未受影响证据保留。
